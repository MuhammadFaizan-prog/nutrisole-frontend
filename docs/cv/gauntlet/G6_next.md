# G7 plan (proposed after the G6 closeout; not run)

State after G6: champion unchanged (G3 control detector 640 -> 480 raw+NMS, G3 E224 quality classifier T=0.25, scene guard rule 2 off, IouTracker). Every G6 number is sandbox CPU; nothing has been validated on a phone, an emulator, Lahore footage or by human graders.
Ordered by expected real-world value per hour. Blockers that need the user are marked **(user)**.

1. **Lahore field clips (user).** 15-20 phone clips, 10-20 s each, >= 3 markets/days, the produce list in `G6_device_validation_pending.md` item 3. Nothing else measures the real product. Split by market: train vs a locked Lahore test.
2. **Label the web-mandi holdout (user or a labeller).** 15 Commons clips / 14 uploaders / 44 min (`ml/runs/G6/video_benchmark/`); 1 fps boxes + per-segment class and rotten flag, 10% double review. Grow to >= 60 independent recordings from more Commons uploaders (25% cap). Then run G3 control vs any candidate, IouTracker vs ByteTrack, once. This is also the only way to break the tracker tie (item 4).
3. **Human review of the OWLv2 queue (user).** `ml/runs/G6/audit/owl_review_queue_prioritised.csv`: start at rank 1 (G3-conflict and lemon/citrus items); a reviewed subset can enter a NEW train split, never a locked test.
4. **ByteTrack follow-through.** G6 TEST: non-inferior on every video metric, r1 = r2, fewer ID switches (30 vs 43) and half the track churn on real web clips (189 vs 387 births/min), but it fails the pre-registered rule because grade flicker is already 0 for the control (floor) and TTFC p90 is slower (933 vs 760 ms). Next: (a) pre-register a rule that the synthetic clips can actually move (ID switches, frame acc, TTFC p90 cap) or decide on item 2 labels; (b) port the association step to `native/src/cv/pipeline/` behind a flag (off) with a TS parity fixture like `tracker_parity.json`; (c) measure on the phone (`G6_device_validation_pending.md` item 4).
5. **Detector.** Neither G6 fine-tune beat G3 (rp pooled 0.299, rpx 0.310 vs 0.314); rp shows fine-tuning G3 on its own data already drifts. Options: (a) rpx data mix trained **from scratch at 640 with the G3 recipe** (not a fine-tune) with 2 seeds, since rpx's OIV7c/lemon gains are real (oiv7c 0.634 -> 0.784); (b) class-balanced sampling to protect test_rf apple/tomato; (c) a labelled small-object VIEW of `test` (ignore < 6 px boxes), never replacing the locked split. Any candidate still needs 2 seeds + the fixed-frame gauntlet r1/r2.
6. **Citrus family:** UX decision on showing "citrus (lemon/orange?)" when lemon_lime and citrus scores are close (38% of OIV7c lemons are called citrus by G3).
7. **Ripeness:** collect the `nutrisole-g5-ripeness` Kaggle output if it finished (it was still RUNNING on Kaggle CPU at G6 close; see G6.md "Deferred"). Wire it only if valid (>= 50 overripe train images, per-fruit confusion reported) as a separate optional head with an "unable to assess" state; otherwise rerun on Kaggle GPU with a per-fruit taxonomy.
8. **Night classifier:** keep G3 E224 (held-out night_sodium_hard rotten recall 0.983). Next attempt: Albumentations RandomGamma / PlanckianJitter / ISONoise / mild MotionBlur with a reduced-hue arm, evaluated on both held-out lighting families.
9. **Guava:** stays unsupported in the app. rpx detects guava on the Kaggle-side split (0.932, Kaggle T4) but is not promoted; a guava-capable champion needs item 5(a).
10. Annotated demonstration video of the G3 control + chosen tracker on a labelled holdout clip (needs item 2).
